# 058 — MCP `2026-07-28`: cache metadata and an honest protocol list

Proposal `korg:1218`, work item #1215. Slice 2 of the **MCP 2026-07-28 across
the fleet** program (`korg:1220`); kaed (sprint 016) was slice 1 and recorded
the pattern in klams, klams-mcp (#1216) is slice 3.

## Goal

Make korg-mcp actually speak `2026-07-28` — deliberately, with the failure mode
understood — before a dependency bump makes it *claim* to. The bug being
pre-empted is not subtle in effect and entirely silent in presentation: a
Claude Code ≥2.1.227 client that negotiates `2026-07-28`, validates `tools/list`
against that revision's schema and finds the SEP-2549 cache metadata missing
registers **zero tools**, while the session stays up and the instructions
arrive. kaed lost its whole surface that way (`korg:1212`). korg is the
highest-blast-radius server of the three: every agent session uses it.

## What the proposal got wrong, and it mattered

The plan (and the klams knowledge kaed wrote) assumed korg was on rmcp ≥3.1.0,
where the two fields already exist and the work is "hand-write `list_tools`,
set them". korg was on **rmcp 1.7, resolving to 1.8.0**, which has neither
`ttl_ms`/`cache_scope` on any result nor a `supported_protocol_versions()` hook
at all. So this slice had a dependency migration in front of it that neither
sibling slice has.

Two facts from reading the vendored 1.8.0 source, both load-bearing:

- **1.8.0 already knows `V_2026_07_28`** and lists it in `KNOWN_VERSIONS`. What
  saved korg was not ignorance of the revision but the *absence of the hook* —
  with no `supported_protocol_versions()`, 1.8 answers whatever `get_info()`
  says, which was `ProtocolVersion::default()` = `LATEST` = `2025-11-25`. So the
  klams note's "korg-mcp escaped because its rmcp tops out at 2025-11-25" is
  right about the outcome and wrong about the mechanism.
- Which means the trap did not merely stay armed across the bump — **the bump
  springs it**. On 3.1.2 the default `supported_protocol_versions()` is
  `KNOWN_VERSIONS`, so the moment `cargo check` passed, korg was advertising
  `2026-07-28` and serving a `tools/list` without the fields. The two new tests
  failed on exactly that, at exactly that commit. The upgrade and the fields are
  therefore *one* change and were never separable.

## The rmcp 1.8 → 3.1.2 migration

Smaller than its version numbers suggest — three call sites, because korg's
rmcp surface is four `ServerHandler` methods and the transport wiring:

- `model::Content` → `model::ContentBlock`.
- `call_tool` returns `CallToolResponse`, the MRTR envelope 3.x introduced.
  Every korg tool completes in the request that made it — no elicitation, no
  SEP-2663 tasks — so it is always `Complete`, and stripping `resultType` back
  off for a legacy peer is rmcp's job (`strip_result_type_for_legacy_peer`).
- `StreamableHttpServerConfig::with_stateful_mode(false)` →
  `with_legacy_session_mode(false)`. Renamed, not re-specified: SEP-2567 removes
  sessions from `2026-07-28` outright, so the flag only ever governed the legacy
  lifecycle. Same value, honester name.

Worth recording for slice 3: the klams knowledge was measured against **3.1.0**,
and `Content` → `ContentBlock` plus `CallToolResult` → `CallToolResponse` are a
**3.1.0 → 3.1.2** delta it therefore does not mention. Check the version you
actually resolve to, not the one the note was written against.

## Decisions

**D-1 — State the supported list; pin the ceiling.** `SUPPORTED_PROTOCOL_
VERSIONS` and `FALLBACK_PROTOCOL_VERSION` are korg constants, not rmcp's
defaults. rmcp's default is a claim about the *SDK*; serving it makes korg
assert things only the SDK knows, which is the entire causal chain of #1212.
The fallback is pinned for the same reason kaed pinned its own (015 D-3):
`LATEST` moving underneath a server is how this bug class arrives — through a
dependency bump, with no code change for anyone to review. Raising korg's
ceiling should be an edit to two adjacent lines, made on purpose.

**D-2 — Emit cache metadata only to peers that negotiated `2026-07-28`.** A
`2025-11-25` peer is entitled to `2025-11-25`'s shape. korg now serves a newer
revision than several of its clients ask for, which means it owns the
translation in both directions; rmcp strips the neighbouring `resultType` field
for legacy peers on precisely this reasoning, but it does **not** strip cache
metadata, so that half is korg's. Gated on `RequestContext::protocol_version()`,
which is correct under both lifecycles (inline reports the request's own `_meta`
version, legacy the session's negotiated one).

**D-3 — `cacheScope: public`, TTL one hour.** Not a shrug in either half.
`tools()` builds an identical list on every call, so the catalogue is fixed per
build and there is nothing caller-specific to leak into a shared cache; an hour
is an honest under-claim bounded by how often korg is redeployed.

**D-4 — Negotiate inside the `initialize` override.** korg overrides
`initialize` to render the project roster from live data (#674), and that
override predates 3.x adding negotiation to the default it replaces. The
Streamable-HTTP transport happens to re-negotiate on top of whatever a handler
returns, so korg would answer correctly today without this — but that is the
transport's habit, not a contract, and inheriting a fix by luck is how this
override went stale in the first place. Four lines to make the handler right on
its own terms.

**D-5 — Nothing to do about the client-side trap.** The program's slice-1
comment flagged one grep per remaining server: rmcp's `ClientInfo::default()`
requests `LATEST`, so any of these servers that is *also* an MCP client must pin
what it asks for independently of what it serves. korg has no `ClientInfo` in
the tree — it is a leaf server, not a gateway — so this does not apply, and nor
does the relay-framing finding (016 D-4). Checked rather than assumed, which is
what the comment asked for.

## What shipped

`crates/korg-mcp/src/tools.rs`: the two constants, the TTL, an
`emits_cache_metadata` predicate, `supported_protocol_versions()`, a pinned
`get_info().with_protocol_version(...)`, negotiation in the `initialize`
override, and the two fields on `list_tools`. korg has always hand-written
`list_tools` — the `#[tool_handler]` macro generates it only when absent — so
unlike kaed there was nothing to unpick first.

`crates/korg-api/tests/mcp_protocol.rs`, a new suite, all raw JSON-RPC:

- `tools_list_carries_cache_metadata_for_a_2026_07_28_peer` — the tools still
  arrive, `ttlMs` is a **number** (the client's validator rejected `undefined`
  and would equally reject a stringified number) and `cacheScope` is `"public"`.
- `tools_list_omits_cache_metadata_for_a_legacy_peer` — D-2's other half.
- `negotiation_answers_the_revision_korg_implements` — all five supported
  revisions negotiate as themselves; `9999-12-31` comes back as the ceiling.
- `a_real_tool_call_completes_at_2026_07_28` — `get_board` over the conformant
  request shape, which is the half that would break silently if `_meta` handling
  or MRTR framing were wrong.

Raw because rmcp's own client **cannot** drive a conformant `2026-07-28`
session — it omits the per-request `_meta` its own server requires. A test
written against it silently exercises the `2025-11-25` path and passes while
proving nothing; kaed lost a canary battery to exactly that. A conformant
non-`initialize` request needs `_meta` (`io.modelcontextprotocol/protocolVersion`
+ `clientCapabilities`), an agreeing `MCP-Protocol-Version` header, and the
SEP-2243 `Mcp-Method` header (plus `Mcp-Name` for `tools/call`).

Docs: a **MCP protocol revisions** section in `docs/usage.md` (what korg
supports, why the list is explicit, the raw ceiling probe, and the warning that
the list/ceiling/fields are one change) and a transport note in `README.md`
pointing at it.

`just check` passes clean.

## Not done here

**The live gate.** The wire suite proves korg emits the shape; it cannot prove a
client *accepts* it, because there is no conformant `2026-07-28` client in this
workspace to ask. The only real acceptance test is a fresh Claude Code ≥2.1.227
session enumerating all korg tools and completing a call — and it must be a
*fresh* session, since an existing one negotiated at connect time. Per the
program notes, budget for two passes; kaed's first pass met the #1212 gate and
still found a second bug.

**The kubsdb deploy** — see below; done ahead of `/sprint-ship` because the live
gate needs a deployed korg and Ken's client config points at kubsdb, so a
scratch instance on kai would have cost two config changes to gate one build.
Ken's call, with the REST surface as the fallback path: the failure mode is
MCP-only, so even a total tool-drop leaves korg usable and the rollback is a
re-tag.

### Verified live

`post-deploy-check.sh --compare` clean: every row count identical (830 work
items, 30 cards, 4 links, 194 proposals, 38 reports, 42 projects), node count
1122 and `node_id_seq` both unmoved, migrations 27 → 27.

Then this sprint's actual subject, which the fixed script cannot cover — the
protocol behaviour, probed raw against the deployed instance:

| Probe | Result |
|---|---|
| `initialize` asking `9999-12-31` | `2026-07-28` — the ceiling moved |
| `initialize` asking `2026-07-28` | `2026-07-28` — negotiates as itself |
| `tools/list` at `2026-07-28` (conformant `_meta` + SEP-2243 headers) | 53 tools, `ttlMs` **3600000 (int)**, `cacheScope` `"public"` |
| `tools/list` at `2025-11-25` | 53 tools, **neither** field present |
| `tools/call get_board` at `2026-07-28` | `isError: false`, `resultType: "complete"`, real board payload |
| `/`, `/planning`, `/api/health` | 200 |

`ttlMs` typed as an integer is the specific thing worth reading twice: the
client's validator rejected `undefined` and would equally reject `"3600000"`.

And one accidental but real test of "older clients still downgrade cleanly":
**the session that ran this deploy kept working across it.** That session
connected before the deploy, so it negotiated against the *old* build — which
had no negotiation hook and answered `2025-11-25` to everything — and korg is
in stateless JSON mode, so every subsequent call carries that version header
into the new binary. `get_proposal` answered normally immediately after the
container was recreated. A live pre-2026-07-28 peer, mid-session, over the
container swap.

**What this still does not prove** is client *acceptance* — see the live gate
above. korg emits the right bytes; whether Claude Code ≥2.1.227 is satisfied by
them is a question only that client can answer.
